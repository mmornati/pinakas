Documentation · v0.2

Put the board in charge.

Everything you need to run human + agent teams from a GitHub Project with pinakas: install, configuration, agent hooks, CI, and the full reference.

Overview#

pinakas (Greek πίνακας, “board”) makes a Kanban board the single source of truth for human + agent teams. Agents claim cards, move them and record what each story really cost. Hooks and CI checks make sure they can’t skip a step.

LayerWhat it doesSince
pinakas CLIGives agents write access to the board: claim, move, actuals, status, releasev0.1
Agent hooksSession start injects the live board, a pre-tool hook blocks gh pr create for an unclaimed card, a stop hook blocks finishing without actualsv0.1, Copilot v0.2
GitHub ActionMoves the card when a PR opens, goes back to draft or merges, and records durations from timestampsv0.2
Required checkPR closes a card of the board, the card has actuals, risky labels have a human approvalv0.2

All logic lives in the CLI. Each agent tool gets a one-line hook that calls it, so there is one implementation to maintain and a few small wiring files.

Install#

Requirements:

  • Go 1.27 or newer.
  • The GitHub CLI, signed in, with the project scope.
  • A GitHub Project (v2) with a single-select Status field. The default columns are Ready, In Progress, In Review and Done; any names work once mapped in the configuration.
go install github.com/mmornati/pinakas/cmd/pinakas@latest
gh auth refresh -s project

Pin a version (for example @v0.2.1) in CI and in agent setup steps so that every environment runs the same rules.

Configure#

Run pinakas init at the root of the repository. It writes .pinakas.yml and never overwrites a file that already exists.

pinakas init --owner <user-or-org> --project <number> --repo <owner/name>
pinakas status
FlagEffect
--ownerUser or organization that owns the project
--projectGitHub Project number (from its URL)
--repoDefault repository, owner/name
--copilotAlso write .github/hooks/pinakas.json for GitHub Copilot
--workflowAlso write .github/workflows/pinakas.yml

Check that the column names in .pinakas.yml match your board, then run pinakas status: you should see your cards grouped by column.

Claude Code plugin#

The plugin ships two skills and three hooks. Inside Claude Code:

/plugin marketplace add mmornati/pinakas
/plugin install pinakas@pinakas

Skills

  • pinakas-coordinator: picks the next ready story, plans from the board, dispatches one card to one implementer per worktree, and reports from the board, never from memory.
  • pinakas-implementer: claims, builds test-first, opens the PR with Closes #N, and records actuals before stopping.

Hooks

EventCommandEffect
SessionStartpinakas status --hookInjects the live board: what is claimed here, counts per column, ready cards
PreToolUse (Bash)pinakas check-prBlocks gh pr create unless the card is claimed here, assigned and in progress
Stoppinakas check-stopBlocks finishing while the claimed card has no actuals

A block exits with code 2 and the reason on stderr, which Claude Code shows to the agent so it can correct itself.

GitHub Copilot#

pinakas init --copilot   # writes .github/hooks/pinakas.json

Copilot CLI and the Copilot cloud agent load repository hooks from .github/hooks/. pinakas wires sessionStart, preToolUse and agentStop to the same commands with --format copilot, which answers with a deny or block decision as JSON.

The cloud agent also needs pinakas on its path and a token for the board. Install it in .github/workflows/copilot-setup-steps.yml and expose GH_TOKEN:

jobs:
  copilot-setup-steps:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/setup-go@v7
        with:
          go-version: "1.27.x"
      - run: go install github.com/mmornati/pinakas/cmd/pinakas@v0.2.1

The agent workflow#

  1. Pick. pinakas status. Only cards in Ready, whose blockers are done. Prefer the smallest card that unblocks others.
  2. Claim. pinakas claim 42 assigns the card, moves it to In Progress and starts the clock. One card per worktree.
  3. Build. Tests first, then code. Stay in the card’s scope; new work becomes a new issue.
  4. Open the PR. gh pr create --fill --body "Closes #42". The Action moves the card to review.
  5. Record actuals. pinakas actuals 42 --tokens 120000 --first-pass yes --findings major=0,minor=2. Duration comes from the claim timestamp; never estimate it.
  6. Human merges. Agents never merge. The card moves to Done and a timing comment is posted.

Abandoning a card? Run pinakas release --to ready and say why in an issue comment, so the board stays honest about blocked work.

Action and required check#

pinakas init --workflow  # writes .github/workflows/pinakas.yml
  1. Create a PINAKAS_TOKEN secret that can reach the project: a classic PAT with the project and repo scopes, or a GitHub App token. GITHUB_TOKEN cannot read projects owned by a user.
  2. Make pinakas / check a required status check in the branch protection of your default branch.

What the workflow does

Pull request eventCard
Opened, reopened, ready for review, description editedMoved to review
Converted to draftMoved back to in progress
MergedMoved to done, timing comment posted (claim to PR, PR to merge, claim to merge)
Closed without mergeLeft where it is

What the check enforces

  • The description closes a card of the board (Closes #42).
  • Every linked card has actuals.
  • A label from rules.approval_labels has an approving review from a human other than the author.

Reviews re-run the check. Secrets are not available to pull requests from forks, so the workflow is meant for branches of the repository itself. Authors in rules.exempt_authors (Dependabot, Renovate) are skipped.

Commands#

CommandWhat it does
pinakas status [--json|--mine|--hook]Board grouped by column, plus the card claimed in this working tree
pinakas claim <issue> [--force]Assign a Ready card to you, move it to In Progress, start the clock
pinakas move <issue> <column>Move a card (ready, in_progress, review, done or a column name)
pinakas actuals [issue] …Post the story’s actuals as an issue comment. Flags: --tokens, --first-pass yes|no, --findings major=1,minor=3, --agent, --note
pinakas release [--to ready]Drop the claim without actuals
pinakas check-pr, check-stopHook entry points, --format claude|copilot
pinakas sync-pr, check-ciGitHub Action entry points, reading GITHUB_EVENT_PATH (or --event)
pinakas initWrite .pinakas.yml, the Copilot hooks and the workflow; never overwrites

Issues can be written 42, #42 or owner/name#42. The claim is stored inside the git directory, so each worktree (and each parallel agent) tracks its own card and nothing gets committed. --agent defaults to the PINAKAS_AGENT environment variable.

Configuration#

.pinakas.yml at the repository root:

board:
  provider: github
  owner: acme
  project: 3
  repo: acme/app
  status_field: Status
  columns:
    ready: Ready
    in_progress: In Progress
    review: In Review
    done: Done
rules:
  require_claim_before_pr: true        # hook: no PR without a claimed card
  require_actuals_before_stop: true    # hook: no stop without actuals
  require_linked_issue: true           # check: PR must close a card
  require_actuals_on_pr: true          # check: linked cards need actuals
  approval_labels: ["risk:high"]       # check: these labels need a human approval
  exempt_authors: ["dependabot[bot]", "renovate[bot]"]
KeyMeaning
board.providergithub today; GitLab comes in v0.4
board.owner, projectWho owns the GitHub Project, and its number
board.repoDefault repository for bare issue numbers
board.status_fieldThe single-select field holding the column
board.columns.*Map the four roles to your column names
rules.*Turn each guardrail on or off; see comments above

Measuring#

Every story records the same fields so that experiments can be compared: timestamped duration (from claim to actuals), tokens, first-pass success and review findings by severity. At merge, the Action adds durations measured from timestamps only, independent of what the agent reports.

Actuals and timing comments carry a machine-readable marker (<!-- pinakas:actuals … -->, <!-- pinakas:timing … -->) that the CI check and future reports parse back. Defects found within 30 days and pinakas report come in v0.3.

Fail-open guardrails#

A broken guardrail must never stop all work. If the hook input is malformed or the board can’t be reached, pinakas prints a warning and checks only what it can verify locally. Outside a repository with .pinakas.yml, the hooks do nothing.

FAQ#

Can several agents work in parallel?

Yes: give each one its own git worktree. The claim is stored per worktree, and pinakas refuses a second claim in a worktree while the first card has no actuals.

Why can’t I use GITHUB_TOKEN?

It cannot read Projects (v2) owned by a user. Use a classic PAT with project and repo, or a GitHub App token.

Does it work with pull requests from forks?

Not for the Action: secrets are not exposed to fork PRs. The workflow is designed for branches of the repository itself, which is how agents work.

What if my agent tool isn’t supported yet?

Call the same commands from its hook system: pinakas status --hook at start, pinakas check-pr before tools, pinakas check-stop at stop. Codex support is planned for v0.3.
